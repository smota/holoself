# Changelog

All notable Holoself releases are documented here.

## [0.12.1] — 2026-11-06

The seven OpenTelemetry packages are now development tooling and are no longer installed with Holoself. The npm 0.12.0 package was built after the tag and also contains operation telemetry from #140, absent from the 0.12.0 release notes. This patch documents that optional loopback-only telemetry and corrects current network claims. The security fixes shipped in 0.12.0 are unchanged; 0.12.0 remains the patched version in GHSA-hrc3-wgqf-mvhq. See [release notes](docs/releases/0.12.1.md).

## [0.12.0] — 2026-11-05

Portable links across machines, field and claim rules in the lens vocabulary, and corrections to heading rules and proposal previews that affect earlier releases. Upgrade every machine before running `link repair`; catalogs rebuild once. See [release notes](docs/releases/0.12.0.md).

- Portable links across machines (#131, [decision](docs/decisions/portable-links.md), [guide](docs/guides/multiple-machines.md)): a self root's `config.json` gains a random `self_id` (`init` writes it; `link setup|add|repair|approve` and the new `holoself machine register` add it), `link.yaml` names the self by `self_context.self_id` and the project by a random root `project_key` and no longer stores `self_context.path`, and a per-user, per-machine self map (`selves.json` in `HOLOSELF_CONFIG_DIR`, `%APPDATA%\holoself`, `$XDG_CONFIG_HOME/holoself` or `~/.config/holoself`; mode 0600, symlink-refusing, malformed treated as empty) records where each self is checked out. Linked readers (CLI, hooks, MCP, Workbench, every `link` subcommand) accept an explicit `--self`/`--root`, then `HOLOSELF_HOME`, then the self map, then a legacy `path`, each only when its `config.json` carries the link's `self_id`, else fail closed with `SELF_NOT_FOUND` (hooks stay silent). `lenses/bindings.json` keys bindings by `project_key` (legacy path keys still resolve); the attestation registry stays per machine and records `project_key`. New `holoself machine status|register|forget`; `link setup` joins a synced link that already names this self without `--force`; `link repair` (with new `--self`, and `--dry-run`) migrates legacy links; `link doctor` reports `path_keyed_bindings` and `holoself doctor` warns while any remain. A `project_key` belongs to at most one project path per machine: a copied project folder gets a new key and inherits no binding or salt, and a key held by two active registry entries fails closed (`PROJECT_KEY_CONFLICT`). Setup prints the lenses it inherits when joining. `link remove` keeps the shared `project_key` binding (`lens unbind` removes it for every machine), and one rule now decides every write of `allowed_lenses`: a command that names the full lens set sets the grant exactly; otherwise an existing active grant becomes its intersection with the binding plus any lenses named on the command, and anything else beyond it, including legacy `link.yaml` lens fields, needs the new `--accept-shared-lenses` flag on `link setup|add|repair|approve|backfill` (never `--yes` alone, never the Workbench). New entries list the lenses they grant. `link backfill` never reactivates a revoked entry, and a targeted `link approve` or `link setup` reactivates it capped at its old grant. Re-attestation previously overwrote grants and no longer does. Legacy path-only links and path-keyed bindings behave exactly as before until repaired. **Upgrade Holoself on every machine before repairing links:** older versions cannot read a `link.yaml` without `self_context.path` or a `project_key`-keyed `bindings.json`.

- Privacy fields consolidation, 0.12.0 stage (#108, [decision](docs/decisions/privacy-fields-and-legacy-mount.md)). Field and claim rules move to the lens vocabulary. Legacy `field_visibility` and `visibility=` keep working unchanged through this release.
  - The runtime reads `field_access` (a field or heading name mapped to `{ access_lenses?, disclosure? }`) and claim markers such as `<!-- holoself-claim access_lenses=a,b disclosure=review-required -->`. Omitted `access_lenses` inherits the document, and omitted `disclosure` is `review-required`, so a rule never inherits `publish-approved`. On publication adapters `content`, `sections`, `claims`, `tags` and `links` all require the rule's own `disclosure: publish-approved`.
  - Both vocabularies on one marker or field resolve to the narrower result. An unknown attribute, lens or `disclosure` in a marker makes the block private and historical, and `validate` reports it. Malformed `field_access` excludes a canonical document with a validation error and restricts a project document to `private`. `_policy.yaml` rejects these rules.
  - `holoself migrate policy` rewrites `field_visibility` to `field_access` and claim markers to the lens vocabulary in the same plan, with the same digest, receipts and byte-identical revert. Only the targeted bytes change, on CRLF, mixed line ending and no-trailing-newline files too. Claim ids and hashes do not change, so pending `replace_claim`, `supersede_claim` and `retire_claim` proposals still resolve. Dry-run output lists the rewrites in `sub_document_rewrites`. Documents without frontmatter get their markers rewritten as well. A malformed marker, a rule that admits no lens and `field_visibility` beside an invalid `field_access` stay in place with a plan warning.
  - `verifyNonAmplification` now compares what each lens and adapter receives through the runtime parser and filters, on all five output paths and with a probe for unregistered lenses. If a heading matched two different `field_visibility` rules, the plan reports coverage loss and needs `--confirm-narrowing`, because `field_access` applies every matching rule.
  - `validate --fix` prints the exact mapping per file and hands off to `holoself migrate policy --dry-run`. It does not migrate those fields; its repair replaces invalid values only, narrowing only. The report sits outside the plan digest (`deprecated_fields` with `--json`). It also no longer repairs a document with broken frontmatter that carries field rules, because the repair would lose them. Such a document stays excluded for a fix by hand.
  - Approved proposals write the new marker, and proposals keep their `visibility` field, so archived records stay readable. Operations without a stated visibility keep the claim's rule, including rules with no legacy name. `knowledge migrate-lenses` also renames lenses in `field_access` and marker `access_lenses=`.
  - The catalog schema version is now 5, so catalogs rebuild once. Sections, claims, tags and links gain an optional `access_rule` when no `visibility` label states their rule exactly, and catalog frontmatter gains `field_access`. A section with a field rule now reports the narrower of the document and rule `disclosure`.
  - The publication narrowing listed in the decision record shipped in 0.11.0 (#106). The narrowing in this stage is listed under the next entry.
- Corrections from the independent review of the 0.12.0 stage (#108).
  - **Correction to released behaviour.** A field rule on a heading now covers the claim blocks under that heading on every output path. From 0.6.0 through 0.11.1, `search` applied only the claim's own rule to such a block, as did the `sources` index of context packets from 0.9.0. `content` applied the heading rule, except to a claim block with a heading of its own, which includes the blocks approved proposals write. Review what those versions delivered if you relied on a heading rule to hide a claim.
  - **Narrower for existing documents.** A field rule on a heading now covers deeper headings until the next heading of its level or above, and a heading inside a claim block no longer ends the rule around that claim. Text under those headings that was delivered before may now be hidden. Review documents whose field rule sits on a high-level heading.
  - **Correction to released behaviour.** A `#` line inside fenced code is no longer a heading, on any path. From 0.6.0 through 0.11.1 such a line ended a field rule on an enclosing heading, so the text after it was delivered in `content` and `search`, and from 0.9.0 in the `sources` index too. Review what those versions delivered if a document with a heading rule contains fenced code. Fences follow CommonMark (backticks or tildes, up to three spaces of indent, a closer of the same character at least as long, with no info string), and an unclosed fence runs to the end of the file.
  - **Narrower for existing documents.** A heading inside a fence ends nothing and creates no section, so section splits and ids can change, and an unclosed fence keeps a rule in force to the end of the file. A line in a fence that carries a ruled name still opens that rule, so a stray fence cannot switch a rule off. A fence opened inside a claim ends with the claim; a fence opened outside continues across a claim block.
  - **A heading rule now starts liberally and ends conservatively, so unusual heading shapes hide more rather than less.** This corrects behaviour in released versions: from 0.6.0 through 0.11.1 only `#` at column 0 started or ended a rule, so a rule on a differently shaped heading never applied, and a `#` line in raw HTML ended one. A rule now starts on any line that could present its name as a heading: any indent, Setext, closed ATX, a missing space after `#`, HTML headings, table header cells, lines holding only emphasis, a `<summary>`-like element or a name and a colon, behind blockquote or list prefixes, and inside fences, raw HTML and comments. It ends only at an ATX heading at column 0, with a space or tab after the hashes, of its level or above, outside fences, raw HTML and comments, with no other heading shape on the line. Unclosed `<pre>` blocks and comments run to the end of the file. A shape that states no level, such as a tag-only line `#salary`, a line such as `My salary history:` or anything inside fenced code, ends at the next real heading of any level. Documents with field rules can show less than before.
  - **Correction to released behaviour.** Names now match through presentation, on both the rule and the line: compatibility forms such as full-width letters and `＃`, invisible format characters, every kind of whitespace, HTML entities and inline emphasis. Field rules also match `**Salary:** x`, `**Salary**: x`, `1. Salary: x`, `> Salary: x`, `- [ ] Salary: x`, `Salary = x`, `Salary - x` and table rows. Before, those shapes were delivered. Lookalike letters from other scripts are not matched.
  - Pieces of a heading or fence split by a multi-line claim block now read as the single line they join into, on `content` as well as the catalog. `content` was wider before.
  - **Correction to released behaviour.** `holoself_proposal_preview` and the unlinked client preview now build `before_block`, `after_block` and `preview` from the text the caller was delivered, on a view of a claim. They used to show the claim as stored, including lines a field rule removes and the marker's lens list, and `before_sha256` and `after_sha256` now hash the delivered text. Through a preview, a change of visibility reports `from` as `not shown`.
  - Approved proposals no longer write a lens list into a claim's `- Visibility:` line, and such a line in an existing body is left out of everything delivered except the owner's own context. Restriction reasons name no field for non-owner callers or on publication adapters. `access_lenses` and `exclude_lenses` in delivered metadata, index entries and search results keep only seeded lenses and the caller's lens.
  - `migrate policy` leaves a document the non-amplification gate refuses out of the plan, with a warning, instead of aborting the whole plan.
  - The `sections` snippet of a long section in a document with field rules is cut after filtering, so a cut can no longer break a heading shape. Those sections keep their full text in the local catalog as `full_text`, which is never delivered.
  - Ordinary text after a claim block that has a ruled heading inside it now appears in `content`. It was already in `sections`, and `sections` is now a subset of `content`.
  - On publication adapters, and for every non-owner caller, delivered claim markers keep only `disclosure`, and `field_access`, `field_visibility` and `access_rule` are left out of delivered metadata and index entries. A linked caller that read `visibility=` from a delivered marker no longer finds it.
  - `migrate policy` leaves out, with a warning, a file that is not valid UTF-8 and a document whose frontmatter does not parse while carrying field rules, instead of losing the rule or aborting the plan. A `field_visibility` that is not a mapping stays, with a warning.
  - `migrate policy --apply` checks every file before the first write and rolls back if a later write fails, so a failed apply changes nothing and leaves no receipt. It compares bytes, and receipts keep prior content as `before_base64`, so revert is byte-exact. Receipts with `before_text` still revert.
  - Replace, supersede and retire refuse a claim whose rule admits no lens, instead of writing `[private]`. `field_access` names with surrounding spaces are rejected, and an empty rule is written in its full form.

- Privacy fields consolidation, 0.11.0 stage (#108, [decision](docs/decisions/privacy-fields-and-legacy-mount.md)). Deprecation timeline: 0.11.0 warns, 0.12.0 rewrites `field_visibility` and claim markers through `migrate policy`, 0.13.0 rejects the deprecated fields and removes the legacy live mount, 0.14.0 drops them from the schemas.
  - `holoself validate` prints one `[warn] deprecated …` line on stderr per document and deprecated field (`visibility`, `public_safe`, `field_visibility`, and claim-marker `visibility=` counted per document), with root-relative paths, the mapped target fields, and a pointer to `holoself migrate policy --dry-run`. Exit status is unchanged.

A restricted `read_scope` or `sensitivity` keeps only the `private` lens. Catalog-excluded documents keep the `--confirm-activation` review and use narrower activation rules (conflicts and restricted metadata fully restricted, missing `visibility` treated as `private`), proven never wider than the exact mapping. `field_visibility` and claim markers are left unchanged until 0.12.0.   - Ordinary catalog sections (no field rule) now inherit the document's access and disclosure instead of the deprecated document `visibility`: a publish-approved document without legacy `visibility: public-safe` now shows its ordinary sections on publication adapters, as its `content` already did. No new text crosses the boundary (`sections` stays a subset of `content`). Catalog claims, tags and links (and the search text built from them) now carry the visibility of the line they come from, narrowed by `field_visibility` heading and `Field: value` line rules exactly as delivered content is, on every adapter; this also closes an earlier gap where a hidden field line's text, tags and links surfaced through `tags`, `claims`, `links` and `search_text` (including `--manifest`) on the generic adapter and on legacy `visibility: public-safe` documents. The catalog schema version is now 3 (`schemas/catalog.schema.json`), so every existing catalog is rebuilt once on first use after upgrade and no stale unfiltered annotations survive; `index status` reports `schema_version: 3`.
  - The legacy live mount is deprecated: `link --target` and `unlink --target` print a stderr warning naming the removal version (0.13.0) and the replacement `holoself link setup --project <dir> --self <path>` on every run, including `--dry-run`; `LEGACY_MOUNT_DETECTED` errors and `link status` (`mode: legacy-mount`, new `deprecation` field) carry the same warning. Behaviour is otherwise unchanged.

Any other lens returns `LENS_NOT_GRANTED`; tool arguments never carry identity. `holoself_status` reports `identity: client:unlinked`, the client name, lens and proposal mode without paths. Successful client context calls append served-context ledger entries under the self root with `surface: mcp` and `client_id`; `holoself ledger --root <self> --client <id|name>` filters them. Proposals are disabled by default (`CLIENT_PROPOSALS_DISABLED`, tools not listed); with `--proposals inbox`, `holoself_proposal_create` appends one claim to an existing lens-visible document with required evidence (1–4,000 characters, `EVIDENCE_REQUIRED`, `SECRET_REJECTED`), writes to `<self>/proposals/inbox/` with `origin` and provenance `client:<id>`, uses one `PROPOSAL_TARGET_INVALID` error for every invalid target, and caps pending proposals at 50 per client (`CLIENT_INBOX_FULL`; the check and the write share a lock, `.holoself/client-inbox.lock`). The owner reviews them with `holoself proposals list|show|approve|reject|defer|supersede --inbox --root <self>` (same preview hash, transaction, archive and receipts; Workbench API routes accept `inbox`). The Workbench lens removal refuses a lens used by any client entry (`CLIENT_LENS_IN_USE`). `capabilities --json` lists the `client` command group and `mcp.unlinkedClients`. - Session-end harvest prompt (#72): `holoself mcp` now advertises `prompts: { listChanged: false }` in `initialize` and implements `prompts/list` and `prompts/get` on the main thread for `holoself_session_harvest` (with optional single-line `focus` ≤ 200 characters; unknown arguments and reserved claim/instruction markers are rejected with `-32602` `INVALID_ARGUMENT`, and `HOLOSELF_MCP_AUDIT_LOG` records `prompts/list` and `prompts/get` without arguments). The deterministic v1 prompt instructs the agent to review the session for at most 3 durable, reusable facts about the user (preferences, decisions, stories) evidenced in the session, prefer "propose nothing" when unsure, never infer sensitive identity attributes or invent facts, draft and preview pending proposals via `holoself_proposal_create` and `holoself_proposal_preview` (`append_claim`, `replace_claim`, `supersede_claim`, or `retire_claim` targeting `claim_id`), and remind the user that the owner approves in the CLI or Workbench (no MCP approval tool exists). Non-MCP hosts render the identical prompt with `holoself instructions render --harvest [--project <dir>] [--focus <text>] [--json]`, documented in the "End of session" section of `skills/holoself/SKILL.md`.
- `holoself link setup` now detects and migrates a legacy `.holoself` symlink or Windows junction mount to a bounded metadata link using the same transactional `planSpaceAction` / `applySpaceAction` core as Workbench: it verifies that the mount target is a canonical self root (and matches `--self` when given), prints the full migration and activation plan (`plan_hash`, `.holoself` replacement, and created files), honours `--dry-run` and `--yes` / interactive confirmation, preflights all managed targets before unlinking, restores the mount on failure, and leaves the canonical self root's contents untouched (#107).
- Optional SQLite FTS5 (BM25) retrieval engine. When `node:sqlite` loads without a flag (Node.js 22.13 or newer) and FTS5 is available, context ranking adds a BM25 bonus (up to 4 points, scaled to the best candidate, ties by source id) to token overlap, and `search` / `holoself_search` match stemmed, diacritic-folded tokens with prefix expansion for terms of 4+ characters and order results by a new `bm25` field. BM25 runs only over the documents and claim-/field-filtered sections that already passed the caller's privacy and lifecycle gates, so hidden documents are never returned, scored, or counted. The derived cache `<self>/.holoself/catalog/fts5.sqlite` (git-ignored, mode `0600`) holds only catalog section snippets, is rebuilt from the catalog freshness inputs, by `index rebuild`, or when missing or corrupt, and is refused through symlinks; an unusable file falls back to in-memory tokenization with identical scores. Rebuilds remove `fts5.sqlite.tmp-*` files older than 10 minutes (never through symlinks). `capabilities --json` adds `index.engine` (`available`, `selected`); `search`, `holoself_search` and `index` output gain `engine` (`fts5` or `deterministic-json`), and FTS5-ranked context receipts carry `engine: "fts5"`; JSON-engine packets are byte-identical to before. `HOLOSELF_INDEX_ENGINE=json` forces the JSON engine, which is also the automatic fallback; the packet-parity golden pins it. The retrieval evaluation gains `--engine json|fts5|auto`, per-engine baselines (`baseline.json`, new `baseline-fts5.json`) and engine-specific `known_gap` lists. FTS5 resolves 1 of the 6 synonym/paraphrase gaps (`synonym-gap-pt-falhas-rede`; mean recall 0.8542 to 0.8750 with the #68 need override) with zero leaks and no per-case recall loss; the other paraphrase gaps need synonyms that stemming cannot supply (#69).
- Directory-level privacy policy defaults (`_policy.yaml`): canonical directories (`profile/`, `context/`, `history/`, `topics/`, `reference/`, their subdirectories, and the self root) can define `_policy.yaml` defaults for `access_lenses`, `exclude_lenses`, `disclosure`, `sensitivity`, `document_role`, `read_scope`, `task_include`, `task_exclude`, `confidence`, `knowledge_status` (`current`/`historical`), and `temporal_scope` (`schemas/policy-defaults.schema.json`). Nested `_policy.yaml` files replace parent defaults field by field, and document frontmatter overrides inherited fields explicitly. Unreadable, malformed, unknown-key, restricted-widening, or symlinked `_policy.yaml` files fail closed so documents beneath them receive no defaults and report relative-path validation errors. Holoself is now easier to use day to day: you can manage your context through a local Workbench, install its AI skill once instead of copying it into every project, and give AI tools smaller, more relevant context with a clear record of what was shared.

### A local Workbench for managing your context

The optional Holoself Workbench provides a visual interface for the main workflows:

- See whether your self-context and linked projects are healthy.
- Browse independent project spaces and understand their purpose and boundaries.
- Safely edit knowledge and privacy annotations without manipulating raw metadata.
- Review, approve, defer, reject, or supersede proposed knowledge.
- Configure lenses and personal lens instructions.
- Start context-aware conversations through detected local AI tools.
- Follow specific recovery actions when a project is degraded.

The Workbench runs only on your computer, binds to `127.0.0.1`, requires no hosted account, and does not replace the CLI or Markdown source files.

### More relevant context with less unnecessary loading

Holoself now decides whether personal context is required, helpful, or unnecessary for a task.

When context is useful, it:

- Selects sources based on the task, lens, privacy rules, and knowledge lifecycle.
- Uses bounded `small`, `standard`, or `deep` budgets.
- Loads current knowledge by default instead of mixing in outdated material.
- Can return a compact manifest first and expand only selected sources.
- Limits automatic framework injection to the most relevant methods.
- Reuses cached selections when the underlying sources have not changed.

Every selection includes a receipt describing what was selected, the source hashes, estimated size, applied lens and budget, and whether anything was truncated—without copying private document bodies into the receipt.

### Clear lifecycle for knowledge

Personal knowledge can now be marked as current, historical, or superseded. Historical information remains available when explicitly requested, but it no longer appears in normal current-context requests.

Reviewed cleanup is also available. Cleanup plans contain paths, reasons, operations, and hashes—not private document contents. Applying a plan requires the exact approved digest, rejects stale inputs, and produces an immutable receipt. Proposal archives remain protected.

### Install the Holoself skill once

Holoself can install its shared skill at user level instead of creating another copy inside every project.

Existing linked projects can be migrated to this global model through a previewed, transactional workflow. Holoself validates the global installation before removing managed project copies and rolls back if the migration fails.

User-created project overrides and unmanaged file collisions are preserved and reported for review rather than silently overwritten.

### Easier integration with AI tools

Holoself now exposes a small, stable machine-readable interface:

- `capabilities --json` describes the supported local interface.
- `--version --json` reports product and version information.
- `context --self-only` supplies personal context without redundantly including documents already managed by the requesting project or tool.

This makes integration more predictable while keeping Holoself independent of any single AI application.

### Safer context-aware conversations

Workbench connectors can detect supported local CLI, terminal, and desktop tools. Each conversation resolves bounded, lens-filtered context before launching the configured tool.

Executable paths and arguments remain structured, linked spaces are allowlisted, and there is no generic remote-command endpoint.

### Privacy and control remain foundational

- Canonical knowledge stays in local Markdown.
- The CLI performs no network requests.
- The Workbench is loopback-only and optional.
- Stale edits are rejected rather than overwriting newer changes.
- Writes are hash-guarded, validated, and rolled back on failure.
- Durable AI discoveries still require explicit proposal approval.
- Global installation, project migration, cleanup, and corrective actions remain previewed and confirmation-gated.
- Project artifacts remain owned by their projects; only approved reusable knowledge belongs in self-context.

## [0.5.0] — 2026-08-13

Holoself v0.5.0 establishes the local-first architecture and public distribution boundary for the first release.

### Architecture

- Markdown-first private data root for profile, context, topics, references, local extensions, and generated exports.
- Versioned `config.json`, public contrib catalog, self-contained context packets, atomic writes, and review-before-save workflow.
- Clear ownership model separates user-private data, Holoself-managed files, project-owned instructions, and package-owned public assets.

### Public contrib library

- Ships a catalogued library of synthetic/public framework defaults under `contribs/default/`.
- `init --contribs`, `--exclude-contrib`, and `upgrade` provide explicit selection and refresh behavior.
- Local contribs remain under the private data root and are never packaged.

### CLI safety

- Migration, linking, and project instruction setup require explicit confirmation (or `--yes` for automation).
- Writes use temporary files and rename; exports are staged and prior exports are backed up.
- Existing non-Holoself paths, symlinks, and junctions are refused rather than replaced. No command sends data, publishes npm, or deploys a site.

### Migration, export, and links

- PersonalOS profile, context, topics, reference, and `me` data map into corresponding private Holoself namespaces without deleting source data.
- Export creates a reviewable `.holoself` project packet containing Markdown profile/context and a context packet; `--packet-only` makes it self-contained.
- `--root-setup` updates bounded markers in project instruction files only after confirmation.
- `link` and `unlink` manage only a link owned by Holoself and pointing at the selected private data root.

### Skill distribution and privacy

- Public `skills/holoself/` instruction is distributed separately from private data and can be installed through skills.sh after review.
- npm package contains source, CLI, public skills/contribs, docs, and release metadata only; private profile, context, topics, references, and local contribs are excluded.
- Project exports and links can expose private context to project tools; review before committing or sharing.

### Tests and known limitations

- Test suite covers initialization, validation, migration safeguards, export refresh and packet-only mode, link safety, contrib selection, and private Markdown boundaries.
- Known limitations: Holoself does not automatically install skills, synchronize data, or provide remote storage; project exports require manual review and each project must be exported separately.
