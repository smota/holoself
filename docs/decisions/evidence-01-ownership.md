# ADR E01: Evidence ownership, storage and retention

Status: D00 contract accepted against commit `54a29a4`; D02 implementation remains candidate work. Issue: #9; date: 2026-09-28.

## Decision

Approved canonical Markdown remains the authority for reusable self knowledge. An original is user-owned evidence; extraction, interpretation and coaching records cannot acquire that authority through storage or retrieval.

Activation requires an explicitly selected, private `evidence-root`, disjoint from the canonical self root, every authorized project root and the package checkout. There is no inferred default or automatic migration. This replaces the plan's suggested nested `.holoself-evidence/`: current `canonicalFiles` in `src/ecosystem.mjs` is allowlisted, but project discovery recursively scans configured Markdown inputs. Nesting would require coordinated exclusions across discovery, export and file opening before even reference registration could be safe. A hidden directory is not a security boundary. The separate root trades one explicit setup choice for a simpler containment rule; it does not prevent whole-home backup or indexing by other tools.

The root contains a versioned `owner.json` binding one self identity, `sources/` manifests, `revisions/` immutable byte references, `snapshots/` explicitly authorized originals, `reviews/` durable fidelity decisions, `interpretations/`, `coaching/`, rebuildable `derived/`, and unpublished `staging/`. Durable records use UTF-8 JSON with explicit fields; an explicit owner export can render readable Markdown with provenance. JSON is operational state, not another self profile. Never put this area in Holoself generic context discovery, package files, repository tracking or default export inputs. Backup is an explicit owner action covering durable records and any opted-in snapshots; caches can be omitted. D02 must validate Holoself context/search/index/export exclusions and registered-project overlap before activation. Third-party backup/index configuration is the owner's responsibility and cannot be guaranteed by location.

Owner setup records the absolute root locator and root UUID in private self configuration only after preview. CLI resolves canonical self through the existing resolver, then its explicit evidence binding; a supplied setup path must match that binding on later operations. No environment/home guesses or client-provided override. The evidence root's owner marker must match self identity; moving it requires explicit owner rebind and validation. Owner status/doctor reports the durable-versus-derived inventory and backup/export destination; linked clients receive no private paths. D02 defines the versioned configuration extension and commands before implementing activation; D00 does not modify current config readers.

Creation requires a nonexistent destination or an empty directory. An existing nonempty directory requires a matching owner marker and schema; unknown ownership, wrong owner, unsupported version or any collision fails without overwriting. Resolve roots and inspect every path component, including root ancestors, before creation/open. Reject symlinks, junctions/reparse points, network/UNC and device paths, alternate data streams, traversal and nonregular files. Relative child paths use portable slash-separated components: no Windows-reserved device names (case-insensitive, including extension forms and superscript COM/LPT digits), control characters, forbidden Windows punctuation or trailing spaces/dots. Ordinary mixed-case names remain valid; D02 must detect case/normalization collisions under the host filesystem before publication. Recheck containment and identity at open/publication to address replacement races; realpath string prefix alone is insufficient. Read handles cannot choose a root. D02 supplies filesystem/race tests; D00 does not claim runtime enforcement.

An immutable `SourceRevision` records source ID, revision ID, hash, length and captured locator. **Immutability belongs to that record, not the external file.** Reference mode stores no original bytes. On reopening, bytes must match the recorded digest; disappearance is `missing`, changed bytes are `mismatch`, never silently the historical original. Mutable availability observations are separate from the immutable revision. A user-authorized move updates the source locator after hash verification, retaining the captured locator and same source identity.

Snapshot mode requires separate explicit consent, copies locally into the managed root, verifies the digest and atomically publishes immutable bytes. A snapshot cannot be substituted with a changed external file. Withdrawal removes retrieval eligibility and invalidates handles/caches, preserving originals and history. Purging derived artifacts, deleting an opted-in snapshot, and deleting the user's external original are separate actions. v1 never deletes external originals. Durable records and dependency tombstones survive derived purges; preview affected proposals/reviews before snapshot purge and mark lost availability. Owner retention continues until explicit action; logs omit bodies and private locators.

## Alternatives and consequences

Reject copying originals by default, nesting evidence under `reference/`, and relying on hidden names. A separate root costs setup and backup work but makes containment and ownership explicit. The root is private storage, not encryption; OS access remains the user's responsibility. Rollback disables the capability, exports durable records, and removes only previewed managed derivatives.
