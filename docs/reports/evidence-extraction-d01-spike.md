# D01 local extraction feasibility spike — candidate, not acceptance

Date: 2026-09-28. Scope: [issue #10](https://github.com/smota/holoself/issues/10), [D00 contract](../specifications/evidence-contract-v1.md), [ADR E04](../decisions/evidence-04-extraction.md). D00 delivery `54a29a4` has explicit human acceptance. This report is a source-checkout experiment; it adds no production parser, runtime dependency, ingestion command, RAG index or approval path. The writer had a bounded extension to measure the user-requested reusable document engine and external memory supervision. Independent testing and Claude review remain D01 gates; the G0 human decision applies if the accepted contract changes materially.

## Reproduce the measured comparison

Use Node 20 or newer from a source checkout. The lockfile and installed modules under `tests/fixtures/evidence/spike/` are source-only and excluded from the product package. Installation is explicit and confined to that directory; parsing makes no network requests.

```sh
npm ci --prefix tests/fixtures/evidence/spike --ignore-scripts
node scripts/evidence-spike.mjs --fixtures
node scripts/evidence-spike.mjs --resource-probe
node scripts/evidence-spike.mjs --timeout-probe
node --test tests/evidence-spike.test.mjs
npm audit --prefix tests/fixtures/evidence/spike --omit=dev
```

The `--fixtures` run and D01 tests verify the committed SHA-256 identities, ZIP structure and authored-unit inventory on the supported Node 20+ floor. If exact byte regeneration is needed, use the fixture builder runtime, **Node 24.19.0 with zlib `1.3.2.1-motley-3246f1b`**:

```sh
node tests/fixtures/evidence/build-realistic.mjs --check
```

That byte comparison is not a supported-runtime check: Node 20.0.0 uses zlib `1.2.13` and produces different DEFLATE bytes on both Windows and WSL2 Linux, while the committed DOCX files remain valid and pass identity/structure/parser checks. Leave the committed fixture bytes unchanged.

For the separate kernel-provider probes, use a local Node 20 executable and an already available provider. On Windows, run `pwsh -File scripts/evidence-supervisor-windows.ps1 -Node <absolute-node20> -Mode worker -Fixture sample.md` and repeat with `complex-deflate-props.docx` and `complex.pdf`; `-Mode timeout -DeadlineMs 250` and `-Mode descendant -DeadlineMs 1000` are synthetic cleanup probes. On Linux with a working systemd user manager, set `D01_NODE` to an absolute Node 20 executable and run `bash scripts/evidence-supervisor-linux.sh worker <fixture>` for each fixture, then `descendant` and `timeout`. These source-only scripts do not install or start a provider; an unavailable provider fails. They are experiment harnesses, not product supervisor implementations.

`--fixtures` compares the D00 authored inventory in `tests/fixtures/evidence/golden.mjs` with actual local `markdown-it`, Mammoth, ZIP/XML and PDF.js outputs. It verifies committed fixture bytes, runs parsers in separate child processes, prints timings, sampled RSS, detected units and losses, and exercises nine small fault cases. A candidate failure is recorded in JSON without masking other candidates. It does **not** certify exact relationship targets, reading order, chart meaning or visual fidelity. DOCX and PDF fixtures are synthetic; the two new DOCX files have DEFLATE members and nonzero ZIP timestamps. The properties variant adds `docProps/core.xml` and `app.xml`, a fixed-width table and a visible red image. Builder bytes can vary with zlib version, so the comparison checks committed SHA-256 identities rather than assuming cross-version compressed-byte equality. D00 stored-only bytes remain unchanged.

The optional reusable-engine check used `docling-slim==2.130.0` with `convert-core`, `format-docx`, `format-pdf`, `format-markdown` extras and `psutil==7.1.0` in an isolated Windows Python 3.12 environment. Exact observed Windows versions are in `tests/fixtures/evidence/spike/docling-windows-requirements.txt`; that file is platform-specific, not a Linux/macOS lock. To reproduce, create a separate Python 3.12 venv, install that requirements file into it, set `DOCLING_ARTIFACTS_PATH` to an existing empty local directory, and run `python scripts/evidence-docling-spike.py` with that venv. The script enables Hugging Face offline flags, blocks socket connections, limits converter input size/page count, selects Docling's **native PDF pipeline** with no layout/OCR/table model, and reports its own sampled RSS. Dependency installation uses the network; conversion does not. There was no model download or private data input.

### Reusable engine: Docling

Docling Slim 2.130.0 converted synthetic Markdown, DOCX and PDF successfully in one guarded Windows process. It used 52 pinned packages in a 323 MB isolated environment, took 1.96 s including imports/conversions and sampled 164 MB peak RSS (10 ms sampling). It emitted a Markdown table and the six DOCX cells. Its DOCX structure included the comment author and a link from anchor text to the comment group, plus the header and picture. It **omitted the authored footnote text** and had no picture-caption link. Native PDF emitted 13 text items, 3 page records, one picture and **zero table objects**; the vector chart received no semantics. It cannot alone meet D00's coverage/relations contract on this fixture. The rich document model is useful as an optional parser adapter, with Holoself-specific coverage and missing-unit checks; there is no evidence for making it the mandatory runtime or retrieval authority. A current upstream source file may contain capabilities beyond the pinned 2.130.0 release; this run is the release evidence.

The project [documents](https://docling-project.github.io/docling/usage/advanced_options/) automatic first-use model downloads for model pipelines and a model-free native PDF option; remote processing requires explicit opt-in. Our guard prevented network connections during conversion and selected the native path. Model-backed layout/table extraction, model provisioning/offline installation, Linux/macOS wheels, transitive license audit and 512 MiB behavior on larger documents were **not tested**. A reusable RAG layer could later provide replaceable chunking/indexing, but source revisions, permissions, locators, coverage and human approval must remain Holoself-owned. D06 is the retrieval/index decision point; D01 does not add a RAG server.

| 512 MiB/job = 536,870,912 bytes | Actual selected MD/DOCX/PDF workers ran under a verified Windows aggregate Job Object committed-memory limit and under WSL2 cgroup v2 `memory.max=536870912`, `memory.swap.max=0`. All completed with 11/11, 16/16 and 15/15 detected units. Windows job committed-memory peaks were 27,676,672 / 41,787,392 / 45,518,848 bytes; WSL2 cgroup peaks were 56,602,624 / 66,764,800 / 69,234,688 bytes. | Kernel-backed local feasibility shown for this tiny corpus. These are different accounting metrics, not a common RSS ceiling. No 512 MiB stress, native Linux, macOS or production launch test. |

Earlier advisory `/proc` and `Get-Process` polling exceeded an 80 MiB (83,886,080 byte) threshold by 3,223,552 and 56,078,336 bytes respectively; a V8 heap flag only limits one portion of memory. Separate kernel probes outside this repository showed a WSL2 systemd user unit with `MemoryMax=80M`, `MemorySwapMax=0` killed a 128 MiB allocation with `oom-kill`/status 9, peak 80 MiB (invocation `ab520e97ace94daf995b80eb0d3655dc`). A Windows Job Object with an 80 MiB **committed-memory** limit denied incremental allocation (`RangeError`), while RSS and Job peak were about 83.8/82.6 MiB. The first Windows 80 MiB probe launched Node before assignment, so it is only allocation-denial evidence after assignment. The new 512 MiB source-only probe gates parser work on stdin until Job assignment and limit verification, but Node startup itself is not suspended. Production must create suspended, assign and verify, then resume. An earlier wait-before-drain probe stalled with redirected worker output; concurrent draining removed the stall, consistent with pipe-buffer backpressure. No identical RSS or zero-overshoot claim follows from these probes. [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html) and [Windows Job Object](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information) document the distinct controls. Docker CLI exists here but its daemon was unavailable; macOS container provisioning was not exercised.

The D01 supervisor-port decision is bounded feasibility: Windows Job Object committed virtual memory, Linux cgroup v2 charged memory with swap disabled, and an explicitly provisioned local Linux container provider on macOS using the Linux metric. The 536,870,912-byte provider budget includes worker and descendants; coordinator memory and disclosed provider VM overhead are outside it. Verify limits before parser work and fail closed when the provider is unavailable. No automatic installation, provider start, image pull, network use or weaker fallback is allowed. The production 60 s deadline starts at job launch, rejects late output and records cleanup separately. These are architecture decisions, **not** implemented product guarantees; the spike has no staged publication path or production stress test. [Podman machine documentation](https://docs.podman.io/en/stable/markdown/podman-machine.1.html) illustrates macOS local VM provisioning, but no macOS provider was installed or tested.

## Licenses, distribution and decision

The isolated npm lock has 56 resolved packages including platform-specific optional canvas packages; 44 are non-optional. The locked versions have npm-reported MIT, Apache-2.0, BSD/BSD-2-Clause/BSD-3-Clause, ISC, Python-2.0, `(MIT AND Zlib)` and `(MIT OR GPL-3.0-or-later)` license expressions. Mammoth is BSD-2-Clause and brings JSZip (choose MIT branch for any distribution), Pako (MIT **and** Zlib notices), plus a Python-2.0-licensed argparse version. PDF.js is Apache-2.0; preserve its license/NOTICE when distributed. Optional `@napi-rs/canvas` is MIT but pulls platform binaries. `npm ci --omit=optional` still ran PDF.js 4 text/operator extraction on Node 20.0; PDF.js 5 failed without canvas even on Node 24. Source-only spike dependencies are outside `package.json` product dependencies and npm package allowlist. `npm audit --prefix tests/fixtures/evidence/spike --omit=dev` reported zero advisories at the final lock. Zero reported advisories is not a maintenance or security assurance for PDF.js 4; a current PDF parser on an isolated worker runtime remains a future measured option. The newest PDF.js 5 release advertising Node 20 (`5.6.205`, requiring >=20.19) had a high [PDF.js advisory](https://github.com/mozilla/pdf.js/security/advisories/GHSA-hq66-cqwq-w95j) in npm audit concerning enabled viewer scripting; this does not establish a PDF.js 4 vulnerability by age alone. PDF.js 6.3.289 requires Node >=22.13/24. Docling Slim is MIT, but its 52-package transitive license/redistribution review is still open; no Docling runtime distribution is approved by this spike.

**Selected parser stack for the proposed Node adapters:** `markdown-it@14.3.2` for Markdown, `yauzl@3.4.0` plus `fast-xml-parser@5.11.1` for DOCX, and `pdfjs-dist@4.10.38` for PDF text/operators. These versions run on the actual Node 20.0 floor and expose the structures needed for later adapters. They are **selected by this spike, not installed into the product**; separate review and product implementation remain. Mammoth may provide an HTML preview but cannot be the DOCX evidence source. Docling Slim is not selected as a mandatory dependency because this pinned release loses the authored footnote and caption relation, carries a 323 MB Python environment, and has unqualified cross-platform provisioning; its comment model warrants an optional adapter study. PDF.js 5.5.207 and 5.6.205 do not fit the current Node floor, with the latter also carrying a high advisory.

**D01 decision:** the selected parser versions and fail-closed supervisor port have bounded feasibility evidence on Windows and WSL2 Linux, so the earlier blanket whole-job containment blocker is resolved at the spike-decision level. This is not a product readiness claim. D03/D04 must implement suspended Windows assignment, provider-limit verification, descendant stress, cancellation and atomic publication; D12 must qualify native Linux and an explicitly provisioned macOS container provider. H2 extraction fidelity also remains a D03/D04 qualification: exact relationships, caption binding, PDF reading order, larger hostile-but-bounded files and human golden review need validation and correction. If a supported provider cannot meet the accepted boundary, return to the product decision rather than weakening it silently. The accepted-base Node 20.0 `node:test` hook issue is separate verification-harness debt.
